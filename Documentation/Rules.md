# Agent Bob — Rules

> **Purpose:** Canonical, human-reviewable rules governing how Agent Bob plans, documents,
> implements, and commits work — for itself (the `main` project, this repo) and for every
> project it manages under `/Projects/<id>/`. This file's content is injected into every
> Planner/Coder dsh chat session at onboarding (budgeted, see `AB_DSH_ONBOARDING_MAX_CHARS`) — it
> is not just a reference doc, it is literally part of those sessions' working context.

---

## A. Workflow rules

| # | Rule |
|---|------|
| **R1** | Every work package is linked from `Documentation/Workpackages/workpackages.md` with a one-line summary. That file is **generated** by the engine on every status change — never hand-edit it. |
| **R2** | Every plan is stored as a work package in `Documentation/Workpackages/WP-NNN.md`, authored from [`_TEMPLATE.md`](Workpackages/_TEMPLATE.md). |
| **R3** | Subtask checkboxes in a work package are ticked `[x]` as each item is actually implemented — never ticked in advance. |
| **R4** | Every user prompt that leads to planning or implementation work is logged in `Documentation/Prompts/NN-title.md`: the original prompt, a summary, decisions made, and the related work package(s). |
| **R5** | Work-package status lifecycle: `pending` → `in-progress` → `awaiting-validation` → (`needs-replan` ↔ `pending`) → `passed` \| `blocked` \| `stuck` \| `skipped`. **`idea`** is a separate, pre-lifecycle backlog state, not a step in it: a WP drafted and filed but not yet meant to be worked — never delegated (`bob <wpId>` on an `idea` WP is a human error, not an automated no-op), never counted as open/schedulable work (dashboard "Open Workpackages" lists and the queue system both only ever recognize the lifecycle states above), and never auto-transitioned by anything. Only a human manually rewrites its `Status:` header to `pending` when it's actually ready to be delegated — at that point it enters the normal lifecycle like any other WP. |
| **R6** | **Definition of Done:** a work package is only `passed` when *all* items in its Verification section pass. |
| **R7** | Every work package carries a human effort estimate and an AI-assistance cost estimate. |
| **R8** | **All git state is owned by the pipeline, never by the coder:** a coder session must never run any git command that mutates repository state or history — `add`, `commit`, `reset`, `revert`, `checkout` (to discard changes), `clean`, `stash`, `merge`, `rebase`, `cherry-pick` — under any circumstances, including to "test" a feature that is itself about git, or to recover from an unexpected git state it finds itself in. Read-only inspection (`status`, `log`, `diff`, `show`) is fine. If the working tree is ever dirty or conflicted in a way the coder didn't cause, or a git operation triggered as part of the feature under test leaves the repo in an unexpected state, the coder must stop, write exactly what it sees to `.bob/runs/<projectId>/<wpId>/OPEN.md`, and end the turn `State: blocked` — never attempt its own recovery, because any command broad enough to fix a real conflict (`checkout -- .`, `clean -fd`, `reset --hard`) also discards every other uncommitted change in the tree, not just the damage it caused. `LocalRunner` itself refuses to start a coder turn on top of unresolved conflict markers, regardless of `--allow-dirty-tree`. Once a work package genuinely reaches `solved` (every task independently validated, not just self-reported), the pipeline (`LocalRunner._commitIfSolved`) makes exactly one commit — scoped to that WP's changed files, message = WP id + title — independently inside every project's own repo, or inside Agent Bob's own repo for `main` work. This is deliberate, not just tidiness: a commit made mid-task, before the independent validator has actually checked the work, can't be cleanly undone if the validator later finds a real problem. **`main` auto-commits too, under a distinguishable identity:** an earlier policy (2026-09-09 through 2026-09-16) skipped the automatic commit for `main` specifically — after WP-009 landed unreviewed as commit 911254f, authored under the human's own git identity — so a human would review the diff and commit by hand instead. In practice this meant nobody committed reliably: fully-passed, independently-verified WPs (WP-085/086) sat uncommitted for hours, at real risk of loss. Reversed 2026-09-16 by explicit user decision: `main` now auto-commits exactly like a managed project, but under a distinguishable `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` of `Agent Bob <agent-bob@localhost>` set on the commit itself — so `git log` can always tell a pipeline-made commit apart from a human-made one, which is the actual thing WP-009's incident needed and never got. The human review this was meant to guarantee still matters — it just happens via the reviewer role (`Documentation/AGENT-DELEGATION-WORKFLOW.md`), before or after the commit, not gated on remembering to run `git commit` afterward. Everything upstream of the commit is unchanged: a `main` work package is planned and implemented through Agent Bob's own dsh Planner/Coder/Validator pipeline (queued and run via `bob`, same as any managed project) exactly like every other WP. **A `main` work package must never be hand-implemented outside that pipeline** — skipping straight to writing the code in an ad-hoc session and hand-editing the WP's `Status:` field to `passed` is not a substitute for a real Coder/Validator run, even for `main`'s own self-development, and produces a WP with no dsh session history and no real token/cost data to show for it. |
| **R9** | Every non-trivial planning or review decision — a tradeoff picked, a scope cut, an assumption made — is appended to `Documentation/Decisions.md` (or `Projects/<id>/Documentation/Decisions.md`) with a timestamp and the WP id it relates to. Planner/Review sessions emit this as a structured block in their response; the engine parses and appends it, the same way it already parses the task-state "Machine Data" block. |
| **R10** | **A feature whose own job is to destroy or reset state must never be tested against real, already-terminal state.** This generalizes R8 beyond git: `bob reset`, a revert command, or anything else that deletes run history, rewrites a WP's status, or discards work must be exercised against a disposable target — a scratch WP created for the test, or a throwaway managed project (`Projects/test-*`) — never against a real `main` WP that's already `passed`, even if the plan is to "restore it after." Found necessary after WP-020's own coder tested `bob reset` directly against real WP-012, permanently deleting its `.bob/runs/main/WP-012/` task-run history (not git-tracked, not recoverable) to verify the reset worked, then only restored the WP's markdown `Status:` field — the file-level truth was fine, but the run-level history is gone for good. "Restoring" the visible surface after a destructive test does not undo the destruction underneath it. |
| **R11** | **Essential, reusable project knowledge lives in `wiki/`, kept small and topic-linked — not duplicated, not left to be rediscovered by reading code.** `wiki/wiki.md` is the root index (a link list, not a knowledge dump) linking `wiki/<topic>/<file>.md` files; each file holds only the essence — a few bullet points with real file references — of one topic. Updated automatically: right after a work package is genuinely solved, `checkAndUpdateWiki()` (in `src/backend/engine/wikiFreshness.js`) gives a dedicated per-project dsh session (`ab_<project>_wiki_librarian`, reused across WPs) that WP's summary and the current wiki index, and lets it decide whether anything clears the bar — most WPs won't, and writing something every time would turn the wiki into noise instead of essence. It must check for an existing topic file first and update it rather than create a near-duplicate. `wiki/wiki.md` is injected into every Planner/Coder onboarding alongside `Documentation/Rules.md` (same truncation mechanism, its own smaller budget — `AB_DSH_WIKI_MAX_CHARS`, default 2000 chars) specifically so a coder checks it before building something that may already exist. The wiki-update step never blocks a WP from being marked `passed` or committed — a failure there (dsh unreachable, a bad response) is logged and swallowed, same non-fatal-by-design posture as the webhook/audit side effects it sits alongside in `_checkTerminalAndFinalize`. **Two-level index:** `wiki/wiki.md` links only top-level topic folders (one line per topic with a one-line description), keeping the root index small by construction; each topic folder (e.g. `wiki/backend/`) gets its own `README.md` listing that topic's files as a mini-index. **File-split policy:** when adding to a topic file would meaningfully grow it past roughly 3000 characters (approximating `AB_WIKI_TOPIC_MAX_TOKENS`, default ~1000 tokens), the Librarian splits it into a same-named folder of sub-files organized by aspect (e.g. `wiki/agents/coder.md` → `wiki/agents/coder/rules.md` + `guardrails.md`) — this is an LLM-driven content decision, never a mechanical character cut. **Pre-Planning drift detection:** in addition to the post-solve trigger, `checkAndUpdateWiki()` (in `src/backend/engine/wikiFreshness.js`) runs right before a WP's Planning session starts, diffing everything since `.bob/wiki-last-scan.json` — a marker file holding the last-scanned commit SHA and a content hash of the uncommitted working tree, both updated after every scan run regardless of whether the Librarian wrote anything (so neither a stale commit range nor a standing uncommitted diff gets re-scanned forever) — via `git diff --name-only` plus `git status --porcelain`, scoped to `Documentation/*.md` (excluding self-regenerating files) and `src/**`. If drift is detected, the Librarian fires with the changed-file list so hand-fixes, direct commits, or inter-WP drift never go stale silently. |
| **R12** | **A coder session must never kill or restart a process by name, or by a PID it has not personally verified belongs to a disposable resource this task itself started.** `Stop-Process -Name node`, `taskkill /IM node.exe`, `pkill node`, or any equivalent broad-match command terminates every Node process on the machine indiscriminately — including the dsh-web server the coder's own turn is running inside of, and the `bob` pipeline process supervising the very task making the call. Found live (WP-047): a coding session, debugging a suspected stale DB connection, ran exactly this — killing dsh-web, the dashboard backend, and its own orchestrator in one shot, with no report ever written (the run died mid-turn, silently, taking every other in-flight `bob` process on the machine down with it). Restarting shared infrastructure is not something a coder turn does for itself, the same way committing is not (R8) — if a coder genuinely suspects a stale server process, it stops and names the concrete symptom in `OPEN.md` instead of acting on the hypothesis. See `Documentation/Decisions.md`'s 2026-09-12 WP-047 entry for the full incident and the follow-up work (defined service start/stop/restart scripts) it triggered. **Sanctioned restart path:** on the DEV Stage box (dev (Tailscale)), which runs under pm2, the safe way to restart the dashboard is `pm2 restart <name>` — scoped to exactly one process, never touching dsh-web or other infrastructure; the process name is discovered dynamically via `pm2 jlist` matching on `server/index.js`, falling back to `pm2 restart 0`. For future production deployments using systemd (agent-bob.de (Tailscale `prod`)), the safe way to restart the dashboard is `systemctl restart agent-bob` — scoped to exactly one process, never touching dsh-web or other infrastructure. For service lifecycle management on systemd-based systems: `install/install-service.sh` installs and starts the unit; `install/uninstall-service.sh --force` removes it (safe to re-run). The unit file lives at `install/systemd/agent-bob.service`. These scripts are production-only tooling, not for the DEV Stage box. These scripts replace ad-hoc process kills as the defined operational path for restarts. On local Windows development machines, use `scripts/backend-start.ps1` and `scripts/backend-stop.ps1` to start/stop the backend API server, `scripts/frontend-start.ps1` and `scripts/frontend-stop.ps1` for the Vite dev server, `scripts/build.ps1` for production builds, and `scripts/full-dev-start.ps1` as a convenience wrapper — all managed via PID files under `.agent-bob/`. |
| **R13** | **Only one work package may be actively running across the *entire* system at a time — every environment combined, not per-machine.** This is stricter than the existing `queue` table's single-global-lock (`queueService.js`'s `isProcessing` is in-memory, per-process — it says nothing about a different machine) and stricter than `wpLock.js`'s file lock (per-machine only, at `.bob/locks/<project>/<wp>.lock` — a different machine's disk never sees it). Neither stops a local direct-CLI run (`node bob.js WP-XXX run/process`) and the dev box's own queue worker from processing two different WPs at the same moment — found live 2026-09-14: WP-062 ran on the dev box (its own always-on queue worker picked up a `queue add`'d entry) while WP-065 ran locally (`node bob.js WP-065 process`) at the same time, undetected by either side, because nothing shared between them said otherwise. No corruption resulted only because the two WPs happened to touch disjoint files — that was luck, not a guarantee. **Sanctioned mechanism:** a DB-backed lock (the only state genuinely shared across every environment), acquired before *any* run starts — whether via the queue worker or a direct CLI invocation — and released only on a terminal state (`passed`/`blocked`/`stuck`/`skipped`) or an explicit stop. A second acquire attempt from anywhere refuses, reporting which host/WP already holds it. **Corollary — sync before starting:** once a work package is finished and committed (per R8, automatically by the pipeline for every project including `main`), *every* environment must `git pull` before the next work package starts anywhere, not just the one that just finished. Starting fresh work on stale state is exactly how the two environments' `Documentation/Decisions.md`/`Documentation/Tokens.md`/`workpackages.md` end up independently diverged and need manual reconciliation at commit time — a direct, avoidable cost of skipping this. See `WP-067` for the concrete lock design. |
| **R14** | **Whatever process advances a work package's status must update the WP file *and* the `workpackages` DB row together, not the file alone.** Today `writeStatusHeader()` (`src/backend/engine/wpParser.js:321-327`) — the single choke point for every file-level status change (`localRunner.js:205` at start → `in-progress`; `localRunner.js:319` at terminal finalize → `passed`/`blocked`/`stuck`; `localRunner.js:495` in the drift-correction audit pass) — only ever touches the `.md` file. The DB's `workpackages.status` column is only as fresh as the last manual `npm run db:reconcile`, which nothing runs automatically mid-pipeline. Found live 2026-09-14: `bob status main` reported `WP-065: pending` while its own file, mid-run, already said `in-progress` with three steps checked off — a genuinely misleading read for anyone checking status through the DB-backed CLI/dashboard instead of the file. See `WP-068`. |
| **R15** | **Keep hand-written source files small: soft cap 175 lines, hard cap 400.** Applies to `.js`, `.ts`, `.jsx` and `.tsx` source files. **Exempt:** migrations, generated/built output, fixtures, lockfiles, and all config/data/style/doc formats (`json`, `yml`/`yaml`, `css`, `md`) — line count says nothing about their complexity. **Soft cap (175):** a file that grows past ~175 lines should be looked at — if it holds more than one topic, split it by topic. Test files are exempt from the soft cap (their length is mostly the count of independent cases) but not from the hard cap. **Hard cap (400):** a file must not grow past 400 lines; a WP that would push it over must split it in the same WP. **Use judgment near the limit:** if a split would be artificial — the file is one cohesive unit (e.g. a class whose methods share mutable state), or only a little over the cap and splitting would scatter tightly coupled code or force awkward cross-imports — keep it whole and record why in the WP's Decisions section (R9). Size is a smell, not a goal; never split just to hit a number. **Wiring carve-out:** an entry file that only requires modules and mounts/registers them, with no business logic (`server/index.js`, `bobCli.js`, route registries), may exceed the cap — it is a manifest, and splitting it hides what is mounted. Keep logic out of it. **How to split:** one entry file per feature that only wires and exports (e.g. `pipeline/bobQueue.js`), with concern files in a subfolder named after the feature (`pipeline/queue/tracking.js`, `pipeline/queue/manage.js`); if a concern file itself outgrows the cap, it gets its own subfolder. Shared helpers live in a sibling `shared/` folder, never copied between topics. In React, split into sub-components, hooks and per-topic files the same way. **Never add a new topic to a file that is already over the cap.** A split is a pure move (no behaviour change) in its own commit, with every `require`/`import` path, doc and wiki reference updated. **Existing over-cap files are grandfathered** until a WP touches them substantially, at which point the split duty applies. `bob doctor --sizes` reports current debt (report-only). |

## B. Tech-stack canon

Agent Bob's own stack (the `main` project — this repo):

| Layer | Choice |
|-------|--------|
| **CLI / engine** | Node.js, `src/backend/` |
| **Dashboard frontend** | React + MUI, Vite, `src/frontend/` |
| **Dashboard backend** | Express, `src/backend/server/` |
| **Database** | MySQL 8.0.46 at `DB_SERVER:DB_PORT` (see `.env.example`) — a derived/queryable cache; `Documentation/` on disk remains the source of truth and every table must be rebuildable by rescanning it |
| **LLM backend** | dsh, model configured via `AB_DSH_MODEL` (see `.env.example`) |

Every **managed project** under `/Projects/<id>/` declares its *own* stack in
`Projects/<id>/techstack.json` (`{"active": ["<name>", ...]}`), each name pointing at a
`techstack/<name>/` knowledge plugin. A project's `Rules.md` inherits this file at scaffold time
and may extend Section B with project-specific conventions — it must never remove Section A.

### Conventions
- **Secrets:** never commit `.env`; every package ships a complete `.env.example` (keys only, no real values).
- **New environment variables:** every var a WP introduces must be added to `.env.example` with a real, non-empty default — unless it's a genuine secret (leave it blank there, per Secrets above) or intentionally optional. You do not need to hand-edit any machine's own `.env` yourself: `loadEnv.js` automatically seeds any key `.env.example` declares a non-empty default for into the real `.env` on the next startup, if that key is missing or blank there. Found necessary live (2026-09-17): three separate WPs each correctly updated `.env.example` but left `.env` itself out of sync, so `bob doctor`'s `checkEnv` failed at the start of the *next* WP delegation until a human noticed and hand-patched `.env` — a recurring manual chore, not a one-off. This does not relax the requirement to update `.env.example` — that's still how a new var's default gets defined at all.
- **Work package naming:** `Documentation/Workpackages/WP-NNN.md`, zero-padded to 3 digits.
- **Prompt log naming:** `Documentation/Prompts/NN-title.md`.

## C. Multi-project isolation

- `/Projects/<id>/` is **gitignored** in Agent Bob's own repo and holds its **own independent
  git repository**, `git init`'d when the project is created. Its commits, branches, and history
  are never visible to, and never affect, Agent Bob's own repo. See `PLAN.md` §0 for the full
  mechanics.
- A project's dsh chat sessions are named `AB <ProjectName> WP <n> Planning` /
  `AB <ProjectName> WP <n> Coding`, and its dsh workspace is scoped to `Projects/<id>/`'s
  absolute path — a Coding session can never read or write outside its own project folder (or,
  for `main`, outside this repo).
- `bob <wpId>` with no project id operates on `main` (this repo). `bob <projectId> <wpId>`
  operates on that project.
